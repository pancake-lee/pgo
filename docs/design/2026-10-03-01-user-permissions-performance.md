# 用户权限聚合性能练习设计

> 日期：2026-10-03。状态：开发与自动验证已完成，待用户运行真实环境压测并查看图表。
> 实施交接：[backlog 任务 47](../backlog.md#47-用户权限聚合性能实验)。
> 关联中枢：[登录性能测试闭环](2026-09-30-01-login-performance-hub.md)。

## 练习目标

客户端负载与监控平台已经通过登录接口跑通。本次练习围绕一个可解释的业务缺陷，完成“低效实现 → 压测发现异常 → 指标缩小范围 → 画像定位 → 修复 → 同负载对照”。

当前登录在约 600 RPS 后超时，是用户环境中的已观察现象，其根因尚未确定。新场景从低速率开始，不沿用这个数值作为容量结论。练习的成功条件是证据能够解释业务开销以及修复效果，不要求同时制造 CPU、内存、数据库和锁四类问题。

## 接口选择与代码事实

使用 `GET /user/permissions`，以重复权限合并算法作为练习对象。

- **权限聚合**：已有跨角色合并权限的业务语义，可以构造重复权限数据并替换聚合算法，无需新增接口契约。
- **任务与换课列表**：当前主要是生成的 CRUD；列表可以暴露全量读取和大响应问题，但画像容易落在 ORM 与序列化，业务算法不足。
- **修改用户名、删除部门关联**：主要是简单写操作，更适合数据库写入与并发正确性练习。
- **登录**：已有准备与鉴权能力，可用于测量前取得 token，不作为本轮持续负载目标。

事实来源：[Proto](../../proto/userService.proto)、[权限实现](../../internal/userService/service/permission.go)、[角色关联查询](../../internal/userService/data/dao_UserRoleAssoc.go)、[项目角色筛选](../../internal/userService/data/dao_UserRole.go)、[权限批量读取](../../internal/userService/data/dao_UserRolePermissionAssoc.go)。

正常权限路径执行三次批量查询，处理函数不查询用户表。默认通过请求内 map 聚合，同一动作后值覆盖前值。练习开关开启后允许请求选择低效列表合并，两种算法的输入与覆盖规则一致。

## 当前方案：逐项扫描列表合并权限

保持现有三次批量查询。低效版本每处理一条权限，都从头扫描已经合并的权限列表，按动作查找已有条目，存在则更新路径，不存在则追加；最终转换为接口要求的 map。

这种“先用列表维护去重结果，最后再转换”的写法对应真实的多来源数据合并错误，额外工作来自权限比较，不靠 sleep、空循环或无关计算拖慢请求。

设读取权限行数为 K，唯一动作数为 U。列表查找的工作量可达到 `O(K × U)`；当所有动作唯一时可达到二次增长。修复为当前按动作直接更新 map 的方式后，聚合预期为平均 `O(K)`。

- **优点**：缺陷与修复都在手写业务聚合路径，便于练习 CPU profile 和算法复杂度判断。
- **局限**：权限集较小时，数据库扫描和序列化仍可能更贵，必须先验证业务热点是否可见。
- **语义约束**：重复动作的更新行为保持一致。主数据中重复动作对应相同路径，避免未定义查询顺序影响返回内容。
- **隔离原则**：只改变聚合算法，不同时注入 N+1、全局锁或缓存，避免根因混杂。

用户已选择本方案。服务的练习开关默认关闭，开启后客户端在同一服务上按请求选择 list 或 map，并核对服务器回传的模式。用户可以先观察低效算法，再切换修复算法对照，普通调用保持默认行为。

## 可运行数据设计

模拟用户从多个岗位角色获得重叠功能权限。固定一个项目，分别给测试用户关联 1、10、50 个角色，每角色包含相同的 500 个动作及路径。

| 数据档 | 角色数 | 读取权限行数 K | 唯一动作数 U |
| --- | --- | --- | --- |
| 小 | 1 | 500 | 500 |
| 中 | 10 | 5000 | 500 |
| 大 | 50 | 25000 | 500 |

这是高重叠的受控测试数据，用于隔离输入放大，不代表真实角色分布统计。各档最终都返回同样的 500 个条目、相同路径与近似相同响应大小，避免把响应变大误认为聚合算法退化。

另做固定 10 个角色、唯一动作数为 100、500、2000 的规模对照，观察列表扫描随 U 增长的影响。这一组响应大小也会变化，必须结合纯聚合测量区分序列化开销。

动作长度、路径长度和权限排列规则固定并记录。增加一个其他项目的角色作为隔离正确性用例，不加入主规模变量。

## 验证与观察方式

### 先确认缺陷可观测

在进入 HTTP 压测前，用相同权限输入比较两个聚合实现的正确性、耗时和分配。纯聚合对照是有意义的验证，它回答“构造的业务缺陷是否足够明显”，防止花时间压一个仍由框架主导的场景。

结果逐键比较，不比较 map 的输出顺序。覆盖重复权限、空权限及不同项目隔离。重复动作不同路径的覆盖规则保持现状，不借性能练习改变业务契约。

如果纯聚合差异不明显，或 HTTP 画像仍由数据库主导，先核对 K、U 和实际调用路径，再合理调整权限规模；不预设业务一定占据最高 CPU 百分比。

### 再观察端到端异常

参考实现与低效实现分别在相同数据下跑 10 RPS，预热 30 秒，正式测量至少 120 秒；同条件重复三次。固定数据库、索引、连接上限、服务资源、日志、超时与负载客户端配置。

低速率下对比三档数据，再使用公共负载能力升压。记录目标与完成吞吐、成功率、P50/P95/P99 和 UTC 起止时间。如果公共自动阶梯起步过高，使用现有单档模式逐档递增，不为此另造负载框架。

候选拐点是延迟曲线明显变陡或吞吐跟不上目标的区间，回到相邻两档复测确认。超时不是练习的必要条件，不必为了制造超时继续加压。

### 用指标和画像建立证据链

预期每请求查询次数仍接近三次，聚合开销和 CPU 随数据规模增长，CPU profile 能找到权限合并的业务调用栈。每请求 CPU 可用进程 CPU 秒增量除以完成请求数近似比较。连接等待可能作为后续排队现象出现，不能据此直接认定为数据库根因。

数据库计数是 GORM 操作口径，没有接口维度标签；只在同实例、无其他业务流量的稳定窗口计算每请求查询次数。精确 SQL 次数在低负载核对。分配变化作为辅助证据，列表扫描问题并不要求出现巨大分配热点。

Grafana 与 Pyroscope 选择同实例和同 UTC 窗口。CPU、heap 沿用 Alloy 持续采集；block、mutex 仅在存在对应等待证据时按需采集。CPU profile 没有明显锁热点是正常结果，当前聚合没有共享业务锁。

现有 dashboard 展示 P95，P99 从 Vegeta 报告读取。画像与指标边界见 [观测数据速查](../observability-data-map.md)。本轮不要求修改监控平台。

### 修复后的同条件对照

在已出现可解释差异的数据档和负载档，恢复直接 map 聚合，保持数据库查询、数据、响应与运行配置一致，再重复相同测量。

重点比较聚合耗时、每请求 CPU、业务调用栈占比、P99 与完成吞吐。框架重新成为火焰图主要部分可能是业务热点消失后的正常变化，需同时看绝对 CPU 开销，不能只比较百分比。

map 容量提示可留作单独的后续分配练习；JOIN、缓存、共享锁均不纳入这次算法修复。

## 验收与交接

- **正确性**：低效版本和修复版本返回相同权限，重复项合并正确，项目隔离和空集合行为一致。
- **业务证据**：纯聚合测量与 HTTP profile 能解释额外比较工作；若热点不可见，先调整实验条件，不能宣布定位成功。
- **单一变化**：各版本的查询方式始终相同，仅切换权限合并算法。
- **修复效果**：同数据、同负载下重复对照，记录绝对开销与波动，收益由实际测量确认。
- **边界**：这是算法性能练习，不要求制造 Go 数据竞争；高并发下性能退化与不安全共享访问是不同问题。
- **收尾**：数据准备、登录取 token 和批次清理在测量窗口外执行，只清理本批次数据。用户自行启动服务，前台 Ctrl+C 停止；受控进程记录 PID，通过 `kill <PID>` 停止。

- **父知识点**：可观测性与性能工程。
- **本轮推荐重点**：重复权限合并、算法复杂度、CPU profile 定位、同负载性能回归。
- **后续独立练习**：N+1 与连接池等待、分配优化、锁竞争。
