# Proto 表归属映射

> 关联任务：[任务 14](../backlog.md#14-gencurd-inferservicename-配置化)。

## 背景

SQL 定义持久化表，Proto 定义服务与接口。表属于哪个服务是两者之间缺失的业务归属信息，不能再由表名前缀猜测，也不应要求用户维护额外配置文件。

## 设计目标

- 将表到服务的归属声明放在用户本来就维护的 Proto 契约中。
- SQL 起步的项目无需预先创建 Proto，首次生成能得到可编译的 default service。
- 未归属表始终可见，用户能在一次生成结果和控制台提示中发现遗漏。
- 用户将表迁移到自定义服务后，下一次生成自动将对应 CRUD 代码迁移到该服务。

## 用户流程

1. 用户维护 SQL 表结构并运行生成器。
2. 生成器读取全部 Proto 中已声明的表归属，并收集数据库中尚未归属的表。
3. 首次没有自定义服务时，生成器创建 `z_defaultService.gen.proto`，将全部表登记到 default service，并生成相应 CRUD 代码。
4. 用户创建或编辑自己的服务 Proto，将所需表的归属声明从 default service 剪切过去。
5. 用户再次运行生成器，生成器按新的归属生成对应服务的 CRUD 代码，default service 只保留仍未归属的表。

## 映射契约

每个服务通过 PGO 提供的 Proto 自定义 option 声明其表集合。该 option 是表归属的唯一持久化事实来源，支持一个服务包含多张表。

`z_defaultService.gen.proto` 是生成器维护的兜底 Proto。其中的映射区包含简短注释，说明用户应将表映射剪切到自定义服务 Proto 后重新生成。生成器只重写自己维护的 default 映射和生成区，不修改用户拥有的服务声明与手写接口。

若同一张表被多个服务声明，或声明了数据库不存在的表，生成器在写入前失败并输出冲突位置。未映射表不报错，统一归入 default service。

## 生成反馈

每次生成结束输出：每个服务包含的表、默认服务中待归属表，以及如何将它们迁移到自定义服务 Proto 的简短提示。默认服务没有待归属表时，输出明确的完成状态。

## 验收标准

- 仅提供 SQL 时，可生成含全部表映射和 CRUD 代码的 default service。
- 将一张表映射剪切到自定义服务 Proto 后，重新生成的 CRUD 代码归入该服务，default service 不再包含该表。
- 未映射表在 default Proto 映射区和控制台输出中均可见。
- 重复映射、未知表和非法服务声明在写文件前以明确错误终止。
