# 共享角色权限的读写混合性能实验

> 日期：2026-10-03。状态：HTTP 数据准备与读写负载已实现，自动验证通过，2026-10-04 用户已运行并观察到 20 RPS 超时，首次流程交付已验收；根因分析与优化待后续对照。
> 实施交接：[backlog 任务 47](../backlog.md#47-共享角色权限读写混合实验)。
> 关联中枢：[性能测试闭环](2026-09-30-01-login-performance-hub.md)。

## 背景与目标

登录压测已经跑通客户端与监控平台，但其业务路径较薄。本实验使用用户权限查询，模拟多个用户共享公共角色，以及管理员修改公共角色权限时的并发访问。

先使用正常 JOIN 和实际索引状态取得首次基线，再逐轮验证索引优化与分表查询的效果。每轮只改变一个因素，保留原始结果，不预设 JOIN 更慢、拆分查询更快，也不要求管理员写入一定造成明显退化。

练习目标是解释三个问题：全库权限规模怎样影响少量权限查询；共享角色被修改时，影响是否局限于相关用户；索引与查询组织方式分别改变了哪些耗时。

## 当前代码事实

事实来源：[接口契约](../../proto/userService.proto)、[权限服务](../../internal/userService/service/permission.go)、[权限修改服务](../../internal/userService/service/z_svc_userRolePermissionAssoc.gen.go)、[权限 DAO](../../internal/userService/data/z_dao_UserRolePermissionAssoc.gen.go)、[建表 SQL](../../sql/user.sql)。

- **权限查询**：默认使用一条生成接口构造的 JOIN；分表对照先查用户角色关联，再筛选指定项目的角色，最后批量查权限并在请求内聚合。分表完整成功路径是三次查询；没有共享权限缓存或业务聚合锁。两种路径按权限主键顺序覆盖重复动作。
- **权限修改**：现有修改接口按权限记录主键更新，再读取该记录作为返回结果。一次正常修改包含一次更新和一次查询，当前业务没有整批角色权限修改事务。
- **索引候选**：建表 SQL 没有为权限关联表的角色关联字段声明索引。实际数据库可能经过独立调整，首次实验前必须记录真实索引，不能直接把文档当作数据库现状。
- **鉴权范围**：当前场景查询权限值，不能代表其他业务接口已经接入完整权限判定。管理员是负载中的业务角色，本实验沿用现有接口鉴权。

## 业务场景与数据关系

20 个项目各设置两组普通用户，另设一个管理员负载身份。

- **热点组**：组内多个用户共享同一组公共角色，管理员修改这些角色的权限。
- **对照组**：使用另一组角色，权限规模与热点组一致，管理员不修改这些角色。
- **背景关联记录**：对于某次查询，其他项目与未分配角色的权限关联记录不属于结果，但与目标数据存储在同一张表中。

用户都查询自己所在项目的权限，项目和角色关系真实存在。每项目划分 5 个热点角色、5 个对照角色及 10 个其他角色，两组角色互不重叠，各组内部共享角色，避免为每个用户复制一套角色权限。

首次使用用户确认的业务规模，100 个权限点在不同项目和角色中复用：

| 对象 | 初始规模 |
| --- | --- |
| 项目 | 20 |
| 每项目角色 | 20 |
| 系统权限点 | 100 |
| 每角色权限 | 100 |
| 角色权限关联记录总量 | 40000 |
| 普通用户总量 | 1000 |
| 每项目热点组用户 | 25 |
| 每项目对照组用户 | 25 |
| 每组每项目共享角色 | 5 |
| 每次查询读取权限关联记录 | 500 |
| 每次查询返回权限点 | 100 |

角色权限关联总量为“20 项目 × 20 角色 × 100 权限点”，不是 40000 个独立交互操作点。每个用户持有本组的 5 个角色，查询得到 500 条关联记录，按动作合并后返回 100 项。相同动作在同组角色中的初始路径一致，重复关联不会增加独立权限点。

对于某个项目的热点查询，500 条关联记录属于目标角色，其余 39500 条属于无关角色或其他项目。它们用于观察查询访问路径，不再额外添加十万或百万行背景数据。

为保证输入等价，两组的动作集合、路径长度与返回条目数相同，角色和权限记录 ID 不同。各项目使用可识别的路径值验证项目隔离。所有数据归属唯一实验批次，仅在隔离测试库中使用。用户数是参与轮换的身份数，读吞吐仍由独立的 RPS 参数控制。

## 查询与管理员写入行为

### 正常 JOIN 查询

从用户角色关联连接到项目角色，再连接角色权限，按用户和项目过滤，只返回权限聚合实际需要的值。接口返回含义与当前实现一致。

用户可以关联多个角色，每个角色又包含多条权限。正确连接返回这些角色对应的权限行，不会因为三张表就自然产生额外乘法膨胀。热点来自查询频率、读取规模、访问路径和共享数据库资源，是否出现由测量判断。

分表查询保留当前批量读取方式，作为后续查询组织对照。两种实现使用相同逻辑数据和返回字段语义，避免把额外字段传输混入 JOIN 比较。

查询实现通过代码内部开关选择，切换后重新编译并重启服务，再复用同一批次负载进行对照。

### 管理员修改

首次复用现有单条权限修改业务，按固定频率轮流修改热点组中选定的权限记录。每次将路径在两个合法、等长的测试值之间切换，动作和角色归属保持不变，确保不是反复写入相同值。

为适配同一动作被多个角色重复授予的情况，每轮选定一个项目及一个动作，依次修改该热点组 5 个角色中的对应记录，使该轮完成后路径值一致，再轮换项目及动作。轮次内允许旧新值并存，修改速率按单条接口请求计数。测量结束时完成当前动作的角色轮次，等待在途写入结束后校验最终权限值。

管理员写入速率独立于读请求速率。首次只有一个写入流，保持单次修改短小，不人为延长事务；整批修改角色权限属于首次结果之后的独立扩展。

准备数据、登录取得 token、正确性抽查、恢复及清理都在测量窗口外执行。同一输出目录自动复用已验证的批次；数据不满足当前规模时先清理再重建，清理失败保留恢复信息。测试默认保留数据，通过独立清理菜单删除。

用户选择通过现有 HTTP 接口准备数据，创建接口的 P95 直接从监控查看。客户端准备统计仅输出成功数量、总耗时及平均墙钟耗时，另输出一次准备及验证成功汇总；阶段开始及每项目完成通过控制台日志提示进度。正式压测只保留负载侧指标作为对照，不额外采集监控数据。

## 首次负载与对照关系

保持正常 JOIN 和真实索引，同时运行读写负载：热点组和对照组各 10 RPS，管理员默认 1 次修改/秒。两个读组与管理员修改各以正式速率的 80% 同时预热超过 30 秒，持续至目标整分钟前 5 秒，停止预热并等待在途请求与当前角色轮次收尾，空等到整分钟后同时测量指定时长，打印预定与实际 UTC 时间；收尾超时记录延迟。

每次运行执行一次读写负载，复用同目录数据并替换旧负载报告。菜单说明读写同时运行，先读取并缓存管理员写入 RPS，再读取读 RPS、测量时长和输出目录。需要升压时同步提高两个读组的速率，写速率保持不变；增加写压力时固定读速率，单独提高管理员修改频率。

自动升压复用同一批数据，每档执行一次读写负载，各档只保存自身负载报告。控制台保留档位、读写目标速率、窗口时间与进度，效果对比主要在 Grafana 与 Pyroscope 观察。

记录目标与实际读写吞吐、错误率和超时。若写入流跟不上目标，报告实际完成写入率；持续高错误率或超时则结束该档，不以压到超时作为成功条件。

## 分阶段优化的判断方式

### 首次基线：寻找实际问题

保留查询组织、索引和数据库配置的真实状态，观察读写负载下两个用户组的结果与数据库资源变化。

首次固定本次确认的数据规模，按阶梯提高读速率，再在固定读速率下比较写压力。没有观察到退化属于有效结果，记录实际执行计划和资源使用，不通过添加任意数量的关联记录制造问题。

### 索引对照：解释扫描开销

只有实际索引与执行计划表明角色权限过滤存在大量无效扫描时，才设计并新增适合查询条件的索引。在相同 JOIN、数据与读写负载下复测。

索引收益比较查询实际处理行数、数据库操作耗时、读延迟和连接等待；同时记录写入成本变化。若目标索引已存在，不删除它制造缺陷，记录该优化不适用于当前基线。

### 查询组织对照：比较 JOIN 与分表批量读取

在相同索引条件下重复同一读写实验，比较单条 JOIN 与现有分表批量查询。正常成功的 JOIN 预期一次查询，分表路径预期三次，具体回调与 SQL 次数在低负载核对。

结论可以是 JOIN 更快、分表更快或差异不显著。接口延迟之外，还比较数据库往返、处理行数、应用 CPU 与分配，不能只用查询次数判胜负。

并发修改下，单条 JOIN 读取一个语句快照；当前三次查询没有被包在同一事务里，可能跨越不同读取时点。首次管理员只修改权限值，角色关联保持固定；若后续比较角色关系修改，先明确一致性要求，再评估实现取舍。

### 后续优化：由结果驱动

若证据指向管理员写入方式、连接池或其他环节，再独立提出下一项优化并复测。本设计的首次交付不预先加入缓存、批量修改业务或新的锁策略。

若本轮场景仍未产生值得分析的性能问题，后续可另行设计业务数据读写前的权限判定，叠加文件路径及父子路径匹配。该方向是后续计划，本轮仍只测试权限读取与管理员修改。

各阶段的实施任务维护在 backlog，本文只记录对照关系和判断标准。

## 指标与画像如何解释结果

现有数据来源见[观测数据速查](../observability.md)。

- **用户侧结果**：热点读、对照读、管理员写三个负载流分别保存完成吞吐、错误率、P50/P95/P99。两组读请求使用同一接口操作名，当前服务指标无法直接区分用户组，组间差异主要从各自客户端报告读取，不给每用户增加指标标签。
- **应用指标**：Grafana 按权限读取和权限修改操作分别看速率、错误和 P95，再看进程 CPU、分配、数据库操作耗时及连接使用。数据准备和清理窗口不计入比较。
- **查询计数**：读写负载包含管理员更新后的回读。正常成功情况下，查询操作总量预计约为“读完成量 × 每读查询数 + 写完成量 × 1”，更新操作量约为写完成量。数据库指标只有操作和结果标签，发生错误或存在其他流量时须单独解释，不能直接除以普通用户读请求数。
- **执行计划**：用实际执行计划解释访问索引、处理行数与循环次数。带执行测量的诊断在负载窗口外或独立诊断窗口进行，避免额外执行查询污染正式比较。
- **应用画像**：Pyroscope 用同实例、同正式窗口的 CPU 与分配画像解释 ORM 扫描、序列化和业务聚合。MySQL 内部 JOIN 执行不会出现在 Go CPU profile 中，业务函数未成为最高热点不代表实验失败。
- **等待来源**：现有连接等待指标表示 Go 数据库连接池等待。确认 MySQL 行锁等待需要数据库侧证据，Go block/mutex 画像也不能直接证明数据库行锁竞争。

热点组与对照组都变慢，优先检查共享数据库资源及连接池；只有热点组显著变慢时，进一步核对该组查询和更新路径。这些是排查方向，不能代替根因证据。

## 读写并发的作用边界

读取同一角色不意味着共享可变 Go 对象，当前聚合 map 属于单请求，因此本实验不预设 Go 数据竞争。

如果实际使用 InnoDB 的 RC/RR 隔离级别，普通 SELECT 通常是 MVCC 一致性读取，不设置读取行锁。管理员修改仍可能通过数据库 CPU、I/O、版本读取与连接资源影响查询，但不能提前宣称更新锁阻塞了普通读。[MySQL 非锁定读取说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)

当前按主键修改属于较轻的写操作，1 次修改/秒可能没有明显影响。首次记录事实，后续是否增加写频率或引入真实批量管理业务，由结果和用户选择决定。

## 正确性与验收

- **用户与项目隔离**：每个用户查询自己的权限，其他项目权限不会进入结果，两组角色互不影响。
- **写入期间结果**：每条返回权限只能是该记录允许的旧值或新值，动作集合与条目数保持固定。首次单条写入不要求整个角色的权限同时切换到同一版本；对照组始终保持原值。
- **写入结束核对**：等待最后一次修改成功后，在测量窗口外检查目标记录及后续查询与最终提交值一致。
- **可解释对照**：三类负载报告和服务指标窗口可关联，区分共享资源等待与数据库行锁，没有证据的机制不写成根因。
- **阶段对照**：首次基线、索引阶段与查询组织阶段使用同条件负载；负载报告在同目录替换，阶段效果按各次运行时间在监控平台比较，记录无收益或没有出现瓶颈的情况。
- **数据与进程收尾**：仅删除本批次测试数据；中断后能凭批次记录恢复清理，已清理批次重复操作直接成功。用户自行启动服务，前台 Ctrl+C 停止，受控进程记录 PID 并通过 kill 停止。

运行操作见[权限场景说明](../../cmd/pgo/performance/permissions/README.md)。数据库实际索引、存储引擎、隔离级别与连接配置尚未核验，首次实验需先记录这些前提，再解释测试现象。
