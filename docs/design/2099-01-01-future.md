# 暂缓/未来需求

## MultiTable

### 多维表格双向同步冲突规则

- **状态**：Approved（已规划，执行前需确定冲突优先级）
- **背景**：`SyncHelper` 只以短时内存标记抑制回环；没有可持久化的版本、修改时间比较或并发写入裁决，因此双端近同时修改会按回调到达顺序覆盖。
- **方案**：为同步记录引入持久化同步元数据（来源、单调版本、修改时间和事件标识），在本地写入和远端回调入口统一比较元数据后决定应用、拒绝或记录冲突；将回环抑制改为使用事件标识和方向，避免依赖 1 秒窗口。冲突、丢弃和重放均写入审计记录，供任务 6 使用。
- **任务列表**：
  - 定义同步元数据的存放方式，以及新增、更新、删除的版本推进规则。
  - 在 `DataProvider`、本地回调和远端回调之间传递并校验元数据。
  - 为同版本、时钟偏差、乱序回调和删除竞争编写自动化测试。
  - **（用户）**确定冲突策略：本地优先、远端优先，或保留冲突等待人工处理；默认不擅自选择业务数据的覆盖方。
- **验收**：双端并发更新、乱序回调和重放事件均得到确定结果；不会产生无限回环；每次冲突可按记录标识追溯。

### 多维表格同步可观测性

- **状态**：Approved（已规划；依赖任务 5 的事件标识）
- **背景**：同步调用失败后仅向调用方返回错误，`pkg/papitable` 不保存失败任务、重试状态或审计轨迹。
- **方案**：围绕任务 5 的同步事件建立持久化投递记录；失败事件按有限次数退避重试，达到上限后进入可查询的待补偿状态。为同步延迟、失败率、积压量和死信数量暴露日志/指标，并由现有 Prometheus/Grafana 部署承接告警。补偿操作必须复用幂等事件标识，不能直接重复执行业务写入。
- **任务列表**：
  - 建立同步事件、投递尝试和最终状态的审计模型。
  - 接入可靠的异步投递与退避重试，保留人工重放入口。
  - 补充指标、结构化日志和告警规则，并覆盖失败、恢复、重复投递测试。
- **验收**：临时故障自动恢复；永久失败可定位、查询和安全重放；告警能区分失败与积压。

### 多维表格多平台适配层

- **状态**：Pending（待明确首批平台）
- **分析**：当前同步层直接使用 `MultiTableDoc`、APITable 事件格式和 APITable 字段表示；仓库没有飞书或企微适配实现，因此该需求真实存在，但没有目标平台、认证方式或字段能力范围，无法形成可验收实现。
- **后续条件**：**（用户）**指定首个要接入的平台及一个真实表格样例。收到后再规划面向共同能力的适配接口、字段映射和平台特性降级边界；不在没有使用方时抽象空接口。

### TEMP 标记方向区分

- **状态**：Approved（已规划）
- **背景**：`UpdateToMTBL` 与 `UpdateToLTBL` 都以同一 `LastEditFrom_TEMP` 表示“对端写回中”；`syncDataProvider.go` 还保留“是否漏设 TEMP”的 TODO。方向无法由标记本身判定，且内存 map 未加并发保护。
- **方案**：以任务 5 的事件标识为主、以方向明确的本地短时标记为辅，分别标识 local→remote 和 remote→local 的写回。把标记的创建、消费、过期和并发访问封装在同一组件；删除与初始化流程也走相同规则，移除含混的 TEMP 分支和 TODO。
- **任务列表**：
  - 替换双向共用的 TEMP 语义，整理本地/远端写回、删除和初始化路径。
  - 为标记存储加并发保护和可测试的过期控制。
  - 覆盖双向更新、回调延迟、重复回调和并发更新的单元测试。
- **验收**：同向回环被抑制，反向人工编辑不会被误跳过；竞态检查不报告标记存储的数据竞争。

## 基础设施

### 排查 BUG 案例建设

- **状态**：Approved（已规划；与任务 15、10 联动）
- **背景**：仓库缺少可重复触发的请求链路诊断样例；现有日志可携带 Kratos TraceID，但 HTTP 响应没有稳定的请求标识。
- **方案**：新增仅在开发/测试环境启用的诊断接口，串行调用三个可控子步骤，并支持注入延迟、并发和确定性失败。入口统一提取或生成 RequestID，将其写入上下文、日志和错误响应；测试验证同一请求的全部日志共享标识，而并发请求彼此隔离。
- **任务列表**：
  - 建立受配置保护的诊断服务和三段内部调用链。
  - 接入 RequestID 传播、日志关联和错误响应字段。
  - 编写并发、延迟、失败注入的集成测试，并在日志采集环境验证查询方式。
- **验收**：单个失败响应返回 RequestID；以该 ID 可查询完整调用日志；并发样例不会串号。

### 日志策略优化

- **状态**：Approved（已规划）
- **背景**：当前 `plogger` 按调用处直接输出，服务默认存在大量 Debug/Info 日志；没有日志分级规范、敏感字段约束、采样策略或请求级诊断缓冲。
- **方案**：先固化生产日志策略：请求完成日志记录结果、耗时和关联标识；业务错误记录可定位上下文；调试细节仅在开发或按采样输出；禁止记录凭证和敏感业务字段。若仍需“成功时不落盘、失败时输出上下文”，实现有容量和过期上限的请求级环形缓冲，且只作为补充，不替代结构化错误日志。
- **任务列表**：
  - 在 `docs/note.md` 记录日志级别、字段、脱敏和采样的项目约定。
  - 统一 HTTP/gRPC 请求完成日志及错误日志字段。
  - 评估并实现有界诊断缓冲，覆盖容量、过期、并发与失败转储测试。
- **验收**：生产日志可按请求标识关联、无凭证泄露；正常流量日志量受控；错误链路保留必要诊断信息。

### 链路追踪

- **状态**：Approved（已规划）
- **背景**：依赖树中有 OpenTelemetry 间接依赖，`RunKratosApp` 已读取 Kratos TraceID 写日志，但 HTTP/gRPC server 未接 tracing middleware，也没有 Trace exporter 或追踪后端。
- **方案**：以 OpenTelemetry 作为应用埋点接口，接入 Kratos HTTP/gRPC 服务端与客户端传播，并以 Jaeger 作为开发环境的追踪后端。启动配置控制采样率、服务名和导出地址；日志字段继续复用同一 trace ID，避免两套关联标识。
- **任务列表**：
  - 增加可开关的 tracing 初始化和资源信息配置。
  - 为 HTTP/gRPC 入站和出站调用接入上下文传播与 span。
  - 添加本地 Jaeger 运行配置、冒烟调用和关闭追踪时的回归测试。
- **验收**：一次跨 gRPC 调用在 Jaeger 中显示父子 span；日志与 trace 可通过同一 ID 互相定位；关闭配置不影响服务启动。
