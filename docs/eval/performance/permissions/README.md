# 权限压测瓶颈定位记录

> 专题入口：[性能测试闭环中枢](../../../design/2026-09-30-01-login-performance-hub.md)。本记录汇总最终保留的 round-01～round-05，包含缺索引基线、索引对照及 JOIN 与独立查询后程序聚合的负载表现。round-04/05 以当前归档和用户最终说明为准。

## 五轮测试

- **round-01，建立可分析的成功窗口**：北京时间 2026-10-07 17:02–17:03，读 40 RPS、写约 5 RPS。两组各 1200 次读取全部成功，[热点组](round-01/hot/11-vegeta-report.txt)与[对照组](round-01/control/11-vegeta-report.txt)整体 P95 分别约 155ms、166ms。末尾短窗口 SQL P95 升到约 568ms，协程从约 36 升到 71，结束后回落。Pyroscope 显示增长主要来自 HTTP 连接；MySQL startWatcher 每次快照保持 2 个，其大额 block delay 是监听完成/取消的累计等待，未显示它是阻塞业务的原因。
- **round-02，提高负载复现错误**：北京时间 2026-10-07 20:29–20:30，读 50 RPS、写约 5 RPS。两组各执行 1500 次读取：[热点组](round-02/hot/11-vegeta-report.txt)有 111 次 HTTP 500，成功率 92.60%；[对照组](round-02/control/11-vegeta-report.txt)有 105 次 HTTP 500，成功率 93%。两组 P95 均约 1.002 秒，失败比例接近；[写入报告](round-02/writer-report.txt)中 300 次请求全部成功。SQL 短窗口 P95 约 1.60 秒，MySQL CPU 约 1.85 个核心，主机 CPU 约 84%，应用 CPU 约 0.20 个核心；连接使用数一度达到 43，协程达到 176，结束后回落。Pyroscope 出现 GetUserPermissions → MySQL readPacket 的等待栈，将调查重点收敛到数据库返回路径。

- **round-03，增加索引后按相同参数复测**：用户确认本轮已增加 role_id 索引，并沿用 round-02 的参数。[运行配置](round-03/00-run.json)记录读 50 RPS、正式时长 60 秒、采样开启；写入报告中仍为约 5 RPS。两组各 1500 次读取全部成功，[热点组](round-03/hot/11-vegeta-report.txt)平均 5.981ms、P95 9.226ms、P99 13.850ms；[对照组](round-03/control/11-vegeta-report.txt)平均 6.238ms、P95 9.069ms、P99 12.952ms。[写入报告](round-03/writer-report.txt)中 300 次请求全部成功，P95 从 round-02 的 66.627ms 降到 7.316ms。这轮是索引优化对照，不是缺索引时的失败窗口。
- **round-04，加索引后 JOIN 的最高已测成功档位**：用户最终保留的[运行配置](round-04/00-run.json)为读 250 RPS、正式时长 60 秒、采样开启；继续提高 RPS 会出现非零错误率。两组各执行 7500 次读取且全部成功：[热点组](round-04/hot/11-vegeta-report.txt)平均 17.243ms、P95 73.685ms、P99 203.336ms；[对照组](round-04/control/11-vegeta-report.txt)平均 17.492ms、P95 73.185ms、P99 214.871ms。[写入报告](round-04/writer-report.txt)中 300 次请求全部成功，实际吞吐 4.99/s、P95 65.809ms。250 RPS 是本轮用户观察到的最高成功档位，不表示已经精确测定容量边界。
- **round-05，各表独立查询后程序聚合**：本次正式负载为北京时间 2026-10-09 11:46:00–11:47:00，[运行配置](round-05/00-run.json)为读 200 RPS、60 秒、采样开启。两组各执行 6000 次读取且全部成功：[热点组](round-05/hot/11-vegeta-report.txt)平均 46.754ms、P95 303.892ms、P99 524.883ms；[对照组](round-05/control/11-vegeta-report.txt)平均 48.205ms、P95 325.055ms、P99 550.404ms。[写入报告](round-05/writer-report.txt)中 296 次请求全部成功，实际吞吐 4.91/s、P95 149.442ms。当前文件已替换此前含 1 次 HTTP 500 的结果；200 RPS 在本窗口零错误，不表示已经确定容量边界。直接获取的 HostMonitor、应用指标和 Pyroscope 分析见 [round-05 监控分析](round-05/20-analysis.md)。


round-01 两组延迟接近，round-02 两组又出现接近的失败比例，更支持共同查询路径的资源压力，尚未显示热点角色写入对热点组造成明显额外影响，不能据此认定锁竞争。两轮均使用约 5 RPS 写入、60 秒正式负载并开启采样，读负载由 40 RPS 提高到 50 RPS。第二轮约 1 秒返回 500，更符合后端约 1 秒 deadline。

## 执行计划将范围缩小到缺失索引

[round-02/explain.txt](round-02/explain.txt)中的同一条 JOIN 显示：

- user_role_assoc 使用 idx_user_role，估计读取 5 条角色关联。
- user_role 使用 PRIMARY，按主键关联并筛选项目。
- user_role_permission_assoc 的 type=ALL、possible_keys=NULL、key=NULL，估计扫描 38473 行，再执行 hash join 和过滤；缺少可用于 role_id 关联的索引。对 InnoDB 表而言，这种全表扫描沿聚簇索引读取表中行，并不等于每次都发生物理磁盘读取。

每个用户目标约为 5 个角色对应的 500 条权限关联，却需要扫描约 4 万条记录。按读 50 RPS 粗略估算，重复扫描规模约为每秒 200 万行，尚未计入管理员回读；EXPLAIN 的 rows 是估计值，实际行数与循环次数待 EXPLAIN ANALYZE 验证。

同一 SQL 独立执行约 27ms，是用户在无压力时的实测。单次耗时较短仍可能包含大量无效扫描；并发下重复扫描争抢 CPU 等资源，查询变慢、在途连接与协程增加，最后超过请求 deadline。27ms 是墙钟时间，不能直接当作 CPU 消耗。Using temporary/Using filesort 是附加成本，现阶段不将它们判定为主因或磁盘排序。

**阶段判断**：round-02 的执行计划支持缺少 role_id 索引导致重复全表扫描的解释；round-03 在用户确认参数相同、增加索引后，两组读取恢复到 100% 成功且 P95 降至约 9ms，进一步支持缺索引是原负载下的主要瓶颈。当前未归档索引后的 EXPLAIN，不能据此写出具体新执行计划或实际扫描行数。

## 索引对照与最终查询方案比较

round-02 → round-03 在相同读写负载下，热点组和对照组 P95 均降低约两个数量级，写入 P95 也下降，索引优化收益得到这组对照支持。round-04 则将有索引的 JOIN 提高至读 250 RPS，两组读取和管理员写入仍全部成功，读速率为 round-03 的 5 倍。

最终保留的 round-04/05 对比显示：

- **读负载与成功率**：JOIN 在 250 RPS 下 15000 次读取全部成功；本次独立查询在 200 RPS 下 12000 次读取也全部成功。JOIN 的设定读速率高 25%，但这不是严格测得的容量提升比例，当前两档不足以确定各自的零错误上限。
- **读取延迟**：JOIN 的平均耗时约 17ms、P95 约 73ms；独立查询即使负载更低，平均耗时仍约 47～48ms、P95 约 304～325ms，P95 约为 JOIN 的 4.1～4.4 倍。
- **管理员写入**：两轮实际写入吞吐接近，分别为 4.99/s 和 4.91/s，且全部成功；独立查询窗口的写入 P95 约 149ms，高于 JOIN 的约 66ms。

**当前结论**：在本次数据规模、测试环境和现有实现下，有索引的 JOIN 表现更好；各表独立查询后程序聚合未体现性能优势。当前独立方案串行执行三条查询，200 RPS 对应最多约 600 次读取查询/秒，而 JOIN 的 250 RPS 约为 250 次读取查询/秒。本次平台画像进一步定位到结果扫描、重复构造查询对象及分配/GC 成本，末段出现连接池等待；细节与硬件边界见 [监控分析](round-05/20-analysis.md)。

两轮都是 60 秒且开启采样，但负载不同，也未在运行配置中保存写入目标速率、实际连接池上限与预热策略，因此结论限定于这些已测窗口，不推广为所有独立查询方案都更慢。后端超时量级沿用约 1s（1000ms）的实验设置；本次 round-05 没有 HTTP 500，不能继续沿用此前失败窗口的错误根因推测。

此前分析中的 round-04 280 RPS 超时窗口及 round-05～08 连接上限探索属于临时结果，已不对应当前最终保留的目录；最终比较使用上述 round-04 的 JOIN 250 RPS 与 round-05 的独立查询 200 RPS。round-04 保留配置及读写报告；round-05 已补充本次窗口的平台查询原始数据与分析。已删除的旧截图与日志不作为当前两档证据。
