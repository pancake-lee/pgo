# PGO — 项目需求文档

## 1. 项目定位

PGO 是个人维护的 Go 工具库与工程脚手架，用于沉淀可复用的基础设施能力，并把重复的后端工程工作收敛为可验证的工具链。它服务于个人项目和小团队原型，而非追求通用框架或替代成熟生态。

## 2. 用户与核心价值

- **主要用户**：维护者本人，以及使用 PGO 初始化或扩展项目的开发者。
- **减少样板代码**：从 SQL/ORM 结构出发生成 CRUD、Proto、HTTP/gRPC、Service 与 Data 的基础链路。
- **统一工程能力**：为配置、日志、数据库、缓存、消息队列与常用第三方服务提供一致封装。
- **缩短项目启动**：通过 `pgo initProj`、Makefile 与部署模板提供可运行的初始骨架。

## 3. 功能范围与优先级

| 优先级 | 能力 | 验收目标 |
| ------ | ---- | -------- |
| P0 | 工程脚手架与构建 | 可初始化项目、生成代码并构建出 `bin/` 产物 |
| P0 | DB-First 代码生成 | SQL/ORM 到 CRUD 链路可生成且生成结果可编译 |
| P0 | 基础设施封装 | 配置、日志、MySQL/SQLite、Redis、RabbitMQ 可被项目复用 |
| P1 | 多维表格建模 | APITable 表结构可导出为可审阅的 MySQL 建表 SQL |
| P1 | 服务端范例 | 用户、任务、换课等服务持续作为生成器和封装的回归样例 |
| P2 | GUI/交互式入口 | 为现有 CLI 能力提供图形或交互式辅助，不替代 CLI |

## 4. 非目标

- 不承诺成为面向公众的通用 Go 框架或稳定 SDK。
- 不以覆盖所有业务场景为目标；生成器只生成基础 CRUD，复杂业务逻辑由项目手写。
- 不在 PGO 内承载具体项目的产品需求或长期任务计划。

## 5. 质量要求

- 生成前校验输入，生成失败不得留下半成品或写入意外目录。
- 既有生成行为的变更必须有兼容性说明和可重复的回归样例。
- 依赖外部服务的功能应明确配置前提；核心工具必须提供清晰的失败信息。
- 文档、Makefile 目标和实际入口保持可追溯一致。

## 6. 演进方向

- 完善 genCURD 的可配置服务名映射与联合主键支持。
- 将现有服务和数据库样例固化为生成器回归 fixture。
- 在不扩大抽象边界的前提下，持续整理基础库的职责与可观测性。
